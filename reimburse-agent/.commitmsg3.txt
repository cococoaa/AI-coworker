支持真实票据上传：PDF 文本提取、建成可审单据、接进现有链路

上传不是"另存一份文件"，而是造出一条能直接进现有审核、任务、查重链路的单据。
为此刻意复用了测试集的结构（claim.json + invoice.txt），没有为上传另写一套流程。

文本提取（internal/upload）
- 只用标准库，不引第三方 PDF 库：交付要单文件，一棵依赖树不值当。
- 处理 PDF 的 Tj/TJ 文本操作符、FlateDecode 压缩流、(...) 与 <...> 两种字符串、
  转义与八进制、UTF-16BE/LE 与 UTF-8。
- 解析 ToUnicode CMap（beginbfchar / beginbfrange）：中文电子发票与
  Chrome/Skia 导出的 PDF 普遍用 Identity-H 编码，内容流里是字形编号，
  不查 CMap 读出来就是乱码。编码宽度按 1 字节与 2 字节都试，全通才采用。

两道"防假成功"的闸门
- 只认内容流：字体（/FontFile、/Length1-2）、图片（/Image、/DCTDecode）、
  元数据（/Metadata）、色彩配置（/ICCBased）、交叉引用（/XRef）一律跳过。
  第一版没做这层，拿真实 PDF 一试提取出 25 万字符的二进制垃圾，长度检查还通过了。
- 要求可读性：提取结果里可读字符占比低于 85% 直接判失败。
  宁可报"读不出来，请转人工"，也不把乱码送进模型——模型会从乱码里
  "抽出"看似合理的字段，那才是幻觉的源头。

上传接口（internal/server/upload.go）
- POST /api/upload（multipart，界面用）与 /api/upload/json（base64，脚本用）。
- 发票必填、佐证凭证可选；单文件 8 MB / 凭证 4 MB，请求体 12 MB。
- 必须能看出发票号码才接受：没有号码就查不了重、验不了真，
  拿一份行程单当发票去审比拒绝更糟。
- 佐证凭证提取失败只警告、不阻断：缺件由规则层按"缺材料"处理，
  但必须说清楚"本次按未提供处理"，不能让人以为已经算进去了。
- 失败分类给出下一步：扫描件/加密 → 说明需要 OCR 或转人工；
  超限 → 413 并提示压缩；无发票号 → 提示确认上传的是发票。

接入现有链路
- 新增 Server.AddCase：上传的单据进内存，/api/audit 能按编号找到它。
- 上传单据 HasTruth=false：没有 truth.json，没有 expected 字段，
  标题与标签现生成（"上传票据 · 交通 · BX…"），界面不会出现空白标题。
- 合成演示模式下启动即提示"上传的真实票据无法审核"，不当场踩坑。

界面
- 新增「上传票据」页签：报销单字段表单 + 发票/凭证两个文件选择。
- 上传成功直接把新单据选中并切到列表，省一次点击。
- 三个页签在窄窗口会挤出视口，改为可换行并加宽左栏（clamp 280–340px，
  1280px 以下单独一档）。

验证
- internal/upload：13 项（提取、压缩流、无文本层、加密、非 PDF、大小、图片、
  发票号判定、幂等落盘等）；internal/server：8 项上传接口测试。
- 真实 PDF 回归：桌面上的真实 PDF（Skia 生成、Identity-H）可读出正文；
  字体子集缺映射的部分会被可读性闸门拦住，如实报错而不是硬猜。
- 交付包实测：上传 PDF → 识别发票号 26157293145980000777 → 建成 UP 单 →
  审核 → 自动建任务（结论 manual_review）→ 落盘无 truth.json。
- go build / vet / gofmt 干净，14 个包测试全绿。

已知限制
- 不做 OCR：图片与扫描件明确拒绝并说明原因。
- 不做字体子集映射（ToUnicode 缺失时）：那需要完整 PostScript 解释，
  收益远小于成本，改由可读性闸门兜底转人工。
- 多字体复杂文档（正文可读、部分字体缺映射）可能整体被拒；
  发票是单一字体，实践上影响很小。
