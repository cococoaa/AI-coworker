# 报销审核 Agent：核心链路说明

本文说明本阶段（11月16日）完成的三个部分：模型接入层、规则引擎、编排层，以及如何跑通一张单据。全部数字来自代码内嵌规则表和本地测试集，可复现。

## 1. 模型接入层 `internal/llm`

DeepSeek 与 Claude 各自用 `net/http` 直连，不引入 SDK 或框架，便于审计每一次请求。

| 项目 | DeepSeek | Claude |
| --- | --- | --- |
| 协议 | OpenAI 兼容 `/v1/chat/completions` | Anthropic Messages `/v1/messages` |
| 结构化输出 | `response_format: {"type":"json_object"}` | `output_config.format`（JSON Schema，GA） |
| 默认模型 | `deepseek-flash` | `claude-sonnet-5-5` |
| 密钥 | 环境变量 `DEEPSEEK_API_KEY` | 环境变量 `ANTHROPIC_API_KEY` |
| 价格（每百万 token，输入/输出） | $0.30 / $1.20（峰时，缓存未命中） | $2 / $10 |

模型名与价格核实于 2026-11-16，来源为 DeepSeek API 文档的 Models & Pricing 页与 Anthropic 定价资料。两者都写在 `config.example.json` 里，现场可改，不用改代码。

**失败处理**（全部有测试覆盖，见 `internal/llm/*_test.go`）：

| 情况 | 分类 | 是否重试 | 对判定的影响 |
| --- | --- | --- | --- |
| 未配置密钥 | `no_key` | 否 | 该模型缺席，关键字段无交叉校验 |
| 超时 | `timeout` | 是（1 次） | 按"状态未知"处理，不当作通过 |
| 401/403 | `auth` | 否 | 同上 |
| 429 / 5xx / 网络 | `rate_limit` `server` `network` | 是（1 次） | 重试耗尽后同上 |
| 返回空白或被 `max_tokens` 截断 | `empty` | 是 | 不猜字段 |
| 返回不是合法 JSON、字段缺失、置信度越界 | `bad_json` | 否 | 该字段不可信 |

配置里出现 `api_key`、`secret`、`token` 之类字段会直接拒绝启动；密钥状态在界面与日志里只显示"已配置 / 未配置"。

**交叉抽取**：两个模型独立抽同一张发票，逐字段比对。比对前只做格式归一化（金额补两位小数、税号转大写），不做任何"模糊匹配"。不一致的字段标记为不可信、值为空，不取任何一边。置信度取两边较小值。

**离线回放** `internal/llm/replay.go`：用于没有密钥时演示和回归。录制按"供应商 + 单据 + Prompt 版本"寻址，Prompt 一改旧录制自动失效；回放时界面必须显示"录制回放，并非本次实时输出"。有密钥时永远优先真实调用。

## 2. 规则引擎 `internal/audit`

引擎读三样东西：抽取后的字段（带置信度与是否一致）、报销单、MCP 工具返回。它不读原始文本去猜，也不调模型。

**与标准答案互相印证**：`mockgen.Label` 只读结构化真值打标准答案，引擎只读"抽取结果 + 工具结果"。同一个口径、两条独立实现。60 条用例上，两者的命中项集合、结论、核准金额必须完全一致，这是 `TestEngineMatchesLabelOnAllCases`。

**不可信就不判**：字段不可信（抽取不到、置信度低于 0.80、两模型不一致）时，依赖它的判定项一律跳过并写明原因；工具失败、超时、未调用时同理。跳过的项全部进入 `Result.Skipped`，写进审核意见的"本次未作判定的项"。只有 R15 兜底转人工。这样不会出现"拿一个猜出来的金额把单据驳回"。

**每条命中都带依据**：`Finding` 含判定项编号、规则名、条款编号、条款原文、一句用实际数值写成的理由。测试强制要求：命中项必须有理由，且理由不能短于 6 个字（防止只写编号）。

**不改口径的两个细节**：

- 发票号不可信时不调用查验与查重工具（拿空串去查会得到"查无此票"，进而误驳回）。
- 购买方税号"读到了但是空的"与"没读到"是两回事：前者照样命中 R02-b，后者跳过。

## 3. 编排层 `internal/audit/pipeline.go`

固定五步流水线，每一步都产生事件：

1. `plan` 按规则表推导本次适用的规则条数、需要调用哪些工具；
2. `extract` 双模型并行抽取，逐字段比对并输出合并值；
3. `tools` 调用核验工具，只对可信且非空的键调用；
4. `aggregate` 逐条判定，命中、跳过、结论各自留痕；
5. `explain` 生成审核意见。

事件 `Event` 带自增序号、阶段、类型、标题、细节、耗时、结构化数据，是界面、日志、回放的唯一数据源。并发产生的序号用原子计数，最终按序排列。

**为什么是固定流水线而不是自由规划**：让模型自己决定调什么工具、什么时候结束，就存在"跳过必查项也能给出通过"的可能。固定步骤保证必查项一个不漏，同时每一步都可观测。

**审核意见的两层保险**：

- 默认由规则结果拼接，条款编号与金额直接取自本次判定，不经模型；
- 可选让模型润色（`-explain`），但生成后做机器核对：意见里出现的每个金额都必须能在判定结果或已核验事实中找到，出现的每个 `R__-x` 编号都必须真实命中；核对不过就丢弃模型文本、退回拼接稿。

## 4. 跑通一张单据

```
go run ./cmd/audit -case data/cases/C01
go run ./cmd/audit -case data/cases/C01 -fault verify_invoice=timeout
go run ./cmd/audit -case data/cases/C01 -disable claude
go run ./cmd/audit -case data/cases/C01 -explain deepseek
```

报告写到 `-out` 指定的 JSON；`-json` 只输出 JSON。

## 5. 当前缺口（如实说明）

1. **真实双模型链路未联调**：当前环境没有 `DEEPSEEK_API_KEY` 与 `ANTHROPIC_API_KEY`。已实现并测通的只有协议构造、错误分类、降级和回放；第一次拿到密钥后要先跑一轮真实调用，确认结构化输出字段被正确接受。
2. **Claude 的 `output_config`**：以公开文档为准，若所用网关或代理不支持该字段，会以 `bad_request` 降级，不会静默放行，但字段质量会下降。届时改为纯 Prompt 约束 JSON 即可，解析逻辑不变。
3. **工具层尚未接入 MCP**：现在用 `cmd/audit/local.go` 读取用例目录的 `world.json` 冒充工具后端，接口 `audit.Explorer` 已定，换成官方 go-sdk 的 MCP 服务即可，编排与规则不用改。
4. **测试集 60 条**：超过原定的 20–30 条，暂未裁剪。
5. **没有真实票据样本**：全部单据为合成数据，规则阈值也是虚构值，评测数字只代表自构造测试集。
