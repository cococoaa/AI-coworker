让审核成为可承接的工作：任务闭环、复核落盘与字段溯源

一次审核从"出个结论就结束"改成"这张单现在卡在哪、卡在谁那里、补了什么之后结论会怎么变"。

任务生命周期（internal/task、internal/server/taskflow.go）
- 七态状态机：待审核 / 审核中 / 待补材料 / 待人工复核 / 初审通过 / 已驳回 / 已撤销，
  每个状态都说明在等谁，界面不用猜。
- 从判定结果推出补件清单：区分"原件未填写""看不清""两模型不一致""整份缺失"，
  四种要的动作不同，不能混成一句"材料不全"。
- 续审计划：因缺件跳过的判定项重查，发票查验与查重必须重查（结果有时效性），
  企业核验可复用。补件后续审不是从头再跑。
- 落盘，重启后仍知道每张单处理到哪一步。

补交必须真的改变结论（internal/server/supplement.go）
- 之前只替换佐证凭证文本，"补申请单号"登记成功、状态也回到待审核，但续审仍拿原始
  单据重跑，R14-b 照样命中——那是假闭环，用户会觉得"我补了你怎么还说缺"。
- 现在按补件类型写回单据：佐证凭证替换正文，claim_info 按 key=value 映射到申请单号、
  事由、人数、招待对象单位等字段，中文键名也认。认不出的键报出来，不悄悄丢掉。
- 补件项带 hint，告诉报销人该填哪些键，而不是给一个空白输入框。

复核结论落盘与幂等（internal/server/review_store.go）
- 复核会写进查重库，"这张票报过"这个事实不能重启就没了，改为落盘到 reviews.json，
  撤销仍是软删除并保留原因，审计能看到谁批的、谁撤的。
- 编号序列跨重启延续，否则 RV0001 撞车，撤销会撤错一条。
- 复核、撤销、补交三处幂等：单据+结论+操作人+意见相同的重复提交返回原记录，
  不新增、不重复回写查重库；补交同内容不推进版本，只有空白差异算同一份。

字段溯源（internal/audit/trace.go）
- 每个抽取值回到送进模型的那份原文里找，给出上下文片段，标 invoice / support / none / empty。
- 财务复核最常问的是"这个数你从哪儿看的"，只回"模型抽的、置信度 0.95"不是证据。
- 只放宽排版差异（千分位、2026年11月1日、空格），数字改了必然报未找到。
- 60 条全量回归：240 个有值字段仅 3 个未找到，且都是发票被污损的用例。

顺带修掉的问题
- 同一单据重复审核会新建任务（C44 攒出三条），改为先查再建。
- SSE 收尾竞态：finish 先广播流结束、后关闭 done，中间窗口读快照得到"没完成、
  没报告"，界面显示空结论。改为先 markDone 再 broadcastClose，并加回归测试。
- hits 序列化成 null 而不是 []：Go 对 nil slice 永远输出 null，改 tag 无效，
  写入前填成空切片。"命中 0 项"与"没有记录"要能分清。
- handler panic 兜底 recover，崩溃时返回 500 并写清路径，而不是让浏览器看到连接被重置。
- 测试共享 data/ 互相污染，改为各自临时目录。
- 交付包漏打包 people.json，导致 dist 里复核一律被拒（默认拒绝，不是故障）。
- 运行时数据 tasks.json / reviews.json 加入 gitignore。

验证：go build 通过，go vet 无告警，gofmt 无差异，13 个包测试全绿。
